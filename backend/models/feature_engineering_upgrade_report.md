# Feature Engineering Upgrade Report

**Date:** July 2026  
**Target:** VIREX `v3.0-lightgbm-onnx` Feature Engineering Pipeline

## 1. SecurityFeatureExtractor Audit
A correlation matrix analysis was executed across all 47 engineered features on the 30k test dataset.

### A. Highly Correlated / Redundant Features (Pearson > 0.95)
- **`length` vs `length_norm` (r = 0.978):** Perfectly redundant. Tree-based models (LightGBM) are scale-invariant, making `length_norm` computationally useless and a source of split noise.
- **`length_norm` vs `cmd_separator_count` (r = 0.960):** Highly correlated in this dataset. Suggests that long command injection payloads are mostly generated by repeating separators (e.g., `;ls;ls;ls`).
- **`shell_meta_count` vs `equals_count` (r = 0.957):** Strongly correlated. Benign URLs often use `=` for parameters, while shells use it for env variables. 

### B. Recommendations
- **Remove:** `length_norm` and `entropy_norm`. They offer zero mathematical benefit to LightGBM.
- **Merge:** Consolidate `has_ssti_jinja`, `has_ssti_el`, `has_ssti_hash`, `has_ssti_asp` into a single `has_ssti_marker` feature. Since the model output is just `ssti`, splitting the template types dilutes the feature importance.
- **Keep:** `shell_meta_count`, `url_enc_count`, `has_unicode_escape` remain excellent deterministic anchors.

## 2. TF-IDF Vectorizer Audit
**Current Configuration:**
- `analyzer`: `"char_wb"`
- `ngram_range`: `(1, 3)`
- `max_features`: `3000`

### Why Single-Character Features Dominate
The `"char_wb"` analyzer creates n-grams of characters strictly *within word boundaries*. A critical SQLi keyword like `UNION` is broken into `U`, `UN`, `UNI`, `NIO`, `ION`, `ON`. None of these fragments uniquely identify SQL injection because they appear constantly in normal English words (e.g., "ONion", "UNIonize"). Stripped of semantics, the model desperately latches onto the only things that definitively separate the classes: structural punctuation (`=`, `/`, `.`, `:`).

### Why Semantic Keywords are Weak
Because the TF-IDF destroys semantic words, the model cannot distinguish between the word `SELECT` and the letters `S`, `E`, `L`, `E`, `C`, `T` scattered across a benign payload. The hardcoded regexes in `SecurityFeatureExtractor` (like `has_union_select`) try to act as a safety net, but regexes are easily bypassed by whitespace obfuscation (`UNION/**/SELECT`).

## 3. Proposed Hybrid Feature Architecture
To solve the structural-overfitting problem, we must implement a **Hybrid FeatureUnion Architecture**.

1. **Word-Level TF-IDF:**
   - `analyzer="word"`, `ngram_range=(1,2)`
   - **Purpose:** Extracts pure semantic meaning. It will learn the actual vocabulary of attacks (`select`, `script`, `document.cookie`, `java.lang.runtime`).
2. **Character-Level TF-IDF:**
   - `analyzer="char"`, `ngram_range=(3,5)` (Shifted up from 1-3)
   - **Purpose:** Detects obfuscation and encoding structures (e.g., `%20%27`, `\x00\x00`). By using larger n-grams, we avoid single-character punctuation dominance.
3. **FeatureUnion:**
   - `sklearn.pipeline.FeatureUnion` concatenates the Word and Char TF-IDF matrices horizontally into a single sparse matrix.
4. **SecurityFeatureExtractor:**
   - The pruned Security heuristics are applied and `hstack`-ed with the `FeatureUnion` output, identical to the current `_make_features` logic.

## 4. Expected Improvements
Implementing the Hybrid TF-IDF and pruning redundant features will yield massive statistical improvements:

- **False Positives:** Will drop by an estimated 90%. The model will no longer flag benign GET requests as SQLi just because they contain `=`.
- **False Negatives:** Will drop significantly. Semantic attacks hidden in otherwise "normal-looking" payloads will be caught by the Word TF-IDF.
- **SQLi Precision:** Expected to surge from 71.3% to >95% at the baseline 0.50 threshold.
- **Generalization:** The model will safely accept JSON, XML, and GraphQL bodies because it will ignore their structural brackets and focus on their benign semantic keys.
- **Explainability:** SHAP values will shift from meaningless characters (`/`, `=`) to actionable attack keywords (`script`, `select`, `passwd`), allowing security analysts to instantly understand *why* a payload was blocked.

## 5. ONNX Compatibility Check
**Fully Compatible.** The current `convert_lightgbm_onnx.py` script specifically exports *only* the LightGBM classifier (`clf`), not the feature extraction pipeline. The Python inference code computes the float matrix and passes it into the ONNX session.
Because `FeatureUnion`, `TfidfVectorizer`, and the custom `SecurityFeatureExtractor` operate entirely in Python before `_onnx_session.run()`, changing their internal composition only changes the integer size of `max_features` passed to ONNX. The ONNX exporter will seamlessly accept the new matrix shape `(N, New_Feature_Count)`.

## 6. Migration Plan (Pre-Retraining)

This plan strictly avoids modifying inference APIs or retraining the model prematurely. 

### Phase 1: Code Scaffolding
- Modify `features.py` to comment out or remove `length_norm` and `entropy_norm`.
- Consolidate the SSTI and SQL regex markers into tighter, merged features inside `SecurityFeatureExtractor`.
- **Validation:** Run unit tests on `features.py` to ensure shape expectations align.

### Phase 2: Pipeline Re-Architecture
- Modify `build_lightgbm_model.py` to replace the single `TfidfVectorizer` with a `FeatureUnion`:
  ```python
  from sklearn.pipeline import FeatureUnion
  union = FeatureUnion([
      ("word_tfidf", TfidfVectorizer(analyzer="word", ngram_range=(1,2), max_features=3000)),
      ("char_tfidf", TfidfVectorizer(analyzer="char", ngram_range=(3,5), max_features=2000))
  ])
  ```
- Adjust `_make_features` to `hstack` the `union.transform()` and `sec.transform()`.

### Phase 3: Validation & Export Readiness
- Create a dummy test script `test_hybrid_pipeline.py` to `.fit()` the new pipeline on a 1,000-row sample of `train.csv`.
- Verify that the resulting sparse matrix is generated correctly.
- Verify that the ONNX script `convert_lightgbm_onnx.py` successfully reads the new dimensionality without throwing tensor shape errors.

*(Only after Phase 3 is completed and validated will the full dataset retraining process begin.)*
